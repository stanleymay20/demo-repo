## 3. Findings

Severity is rated assuming the documented trust boundaries are *not* perfectly maintained by every integrator, which is the realistic deployment case. Each finding has a failing regression test in `test_platform_audit_findings.py` (delivered with this report).

### F1 — HIGH — Policy decision is unauthenticated; forged `PipelineResult` bypasses BLOCK and REVIEW

**Where:** `execution.py:63`, `:215–227`, `:229–272`

`enforce_and_execute()` re-verifies action, payload, manifest, scope, effect and grant against authoritative state. It does **not** verify the policy decision. `decision` and `event.decision` both come from the caller-supplied `PipelineResult`, a plain frozen dataclass with no MAC. The only consistency check (`event.decision != decision.value`) compares two values the attacker controls.

**PoC (confirmed):** evaluate a high-risk prompt-injection against a sensitive action (`send_message`) → legitimate decision **BLOCK**. Rewrite with `dataclasses.replace` to `ALLOW` in both places → `enforce_and_execute` returns **EXECUTED**, executor called once, no review, no approval. Same result turning REVIEW into ALLOW.

**What still held:** the executed payload was the exact host-approved effect. Grant, scope digest, effect allowlist and single-use consumption all still applied.

**Why it matters:** the PR body lists "pipeline results must stay outside agent control" as a boundary. That is an assumption the code does not enforce. Any integrator who serialises a `PipelineResult` across a queue, cache, HTTP hop or plugin boundary silently loses BLOCK/REVIEW enforcement. For a security product, a documented-but-unenforced boundary on the core decision path will be the first thing an external reviewer finds.

**Fix (pick one):**
1. **Single entry point (preferred).** Add `evaluate_and_execute()` that calls `evaluate_request` and `enforce_and_execute` inside one trusted call, and make `enforce_and_execute` private. The decision never exists outside trusted code.
2. **Authenticated evaluations.** Evaluator signs `evaluation_digest(event) ‖ decision ‖ policy_version` with an evaluator key; gateway verifies before reading `decision`. Fits the existing `AuditSigner` key-rotation pattern.

Either fix makes `test_f1_forged_pipeline_decision_must_not_execute` pass.

### F2 — MEDIUM — Multi-use grants allow unbounded dispatch from one evaluation

**Where:** `grants.py:238–246`, `postgres_grants.py:154–169`, `execution.py:274`

For `single_use=False`, `consume()` returns `VALID` without recording anything. One ALLOW evaluation can be replayed until grant expiry.

**PoC (confirmed):** one ALLOW evaluation for `read_data` with a multi-use grant → **50/50** replays executed.

**Mitigating:** sensitive capabilities always route to REVIEW (`policy.py:141`), and REVIEW requires single-use (`execution.py:231`), so this is limited to the NORMAL tier (`read_data`, `summarize`, `list_metadata`, etc.). Not a direct funds-transfer path.

**Still matters:** repeated `read_data` is an exfiltration amplifier, and "replay resistance" is a headline claim in the PR. As shipped, replay resistance holds only for single-use grants.

**Fix:** add `max_uses` (or `remaining_uses`) to `GrantRecord`; decrement atomically in `consume()` under the existing row lock; default 1. Bind the count into `grant_record_digest`. This is also the first step towards the "multi-action budgets" the PR defers.

### F3 — MEDIUM — Grant authorities accept a caller-supplied clock

**Where:** `grants.py:225–246`, `postgres_grants.py:54–58`, `:140–169`; same pattern in `review.py:165–188`

`verify()`, `consume()`, `delegate()` (and `ReviewAuthority.verify()`) accept `now=`. If passed, it replaces the authority clock. The PostgreSQL docstring says validity uses database time after lock acquisition; that is only true when `now` is omitted.

**PoC (confirmed):** issue a grant two hours ago with a 5-minute TTL. `verify()` → EXPIRED. `consume(now=issued + 1 min)` → **VALID**, grant consumed.

`enforce_and_execute` does not pass `now`, so the gateway path is safe today. The risk is the public API: expiry and revocation-window guarantees depend on every caller never passing a clock.

**Fix:** remove `now` from production methods; inject a clock at construction (`GrantAuthority(clock=...)`) so tests can still control time. For `PostgresGrantAuthority`, always use `clock_timestamp()`.

### F4 — MEDIUM — Execution outcomes are not written to the audit chain

`AuditSigner` seals evaluation events with HMAC and optional previous-envelope chaining. `enforce_and_execute` emits no audit record for consume → dispatch → outcome. The tamper-evident trail shows what was *decided*, not what was *done*. If the executor raises after `consume()`, the grant is burned with no record linking the two.

Also: HMAC chaining detects modification and reordering but not **tail truncation** unless the latest sequence/hash is anchored outside the writer's control.

**Fix:** seal an execution envelope (evaluation digest, grant record digest after consume, approval digest, executor outcome/exception class) in the gateway. Periodically anchor the head hash externally (separate DB, object-lock bucket or transparency log).

### F5 — MEDIUM — Symmetric review keys collapse separation of duties

`ReviewAuthority` uses HMAC-SHA256. Any component that can *verify* an approval holds the key and can therefore *mint* one. If the execution gateway verifies approvals, the gateway can approve its own held actions. The PR's own boundary ("grant/review authorities, keys and executors must stay outside agent control") is easier to satisfy, and to prove to an auditor, if the verifier physically cannot sign.

**Fix:** Ed25519 approvals. Review service holds the private key; gateway holds only public keys. Same treatment is worth considering for audit envelopes.

### F6 — LOW — Stray experimental workflow on the GA branch

`.github/workflows/tmp-notebook-run.yml` reconstructs a base64 gzip notebook and installs TensorFlow. It is unrelated to AgentShield, uses unpinned actions, has no `permissions:` block (default token scope), and checks out a different branch (`tmp-notebook-run`). `agentshield-eval.yml` also has unpinned actions and no `permissions:` block.

**Fix:** delete `tmp-notebook-run.yml` from this branch. Pin `agentshield-eval.yml` actions by SHA and add `permissions: contents: read`.

### Observations (no action required)

- Payload snapshotting is careful: exact-type checks block subclass/`__eq__` tricks, non-string keys, NaN/Inf, cycles and depth bombs; canonical JSON with `sort_keys`. The detached snapshot handed to the executor closes the mutation window. Well done.
- Delegation is sound in the cases reviewed: attenuation is subset-checked for both capabilities and effects; parent is disabled on transfer; root-to-leaf `FOR UPDATE` ordering prevents sibling races; depth is bounded even on corrupt storage.
- Effect digests do not normalise Unicode (NFC vs NFD produce different digests). That fails closed for approval, which is correct, but adapters must canonicalise identifiers before computing approved effects or legitimate requests will be refused. Worth a line in `EFFECT_AUTHORIZATION_V1.md`.
- `verify` and `consume` run in separate transactions in the gateway. Not exploitable — `consume` re-validates the full chain under lock — but `consume` alone is sufficient; the earlier `verify` is only needed for the record-digest comparison.

## 5. The 99.999% target — corrected gate definition

The repository docs already frame the target correctly: a **99.999% unauthorized-consequence prevention rate**, not detector recall (`CONTINUATION_2026_10_01.md:82`, `EFFECT_AUTHORIZATION_V1.md:85`). Keep that framing everywhere, including the EIC proposal. "Recall" invites the detector question; "unauthorized consequence" invites the architecture answer.

**What a measured claim requires.** To show the per-attempt unauthorized-consequence rate is ≤ 10⁻⁵ at 95% confidence (exact Clopper–Pearson upper bound), you need this many **independent** adversarial attempts:

| Observed failures | Required attempts |
|---:|---:|
| 0 | 299,572 |
| 1 | 474,385 |
| 2 | 629,578 |
| 5 | 1,051,301 |

Template variants of the same attack are not independent; the effective sample size is closer to the number of distinct attack *strategies* than to row count. And the adaptive-attacker problem means any sampled rate describes only the distribution sampled.

**Recommended split for GA and the EIC:**

- **Claim A — architectural (no sampling needed):** *Given the stated trust boundaries, no effect outside the host-approved allowlist executes, regardless of detector output.* Evidence: F1 fixed (decision integrity enforced), property-based tests over the gateway (Hypothesis: random mutations of action/payload/scope/manifest/grant/decision must never yield EXECUTED for a non-allowlisted effect), and external review. This is where a five-nines-class statement can live, scoped as a design property.
- **Claim B — detector, reported honestly:** recall at a fixed FPR with the 95% lower bound, on held-out data and on external benchmarks the detector was not tuned on (AgentDojo, InjecAgent), plus a separate adaptive-attack result. v27's failed gate and v28's pending evaluation are then evidence of a disciplined promotion process, not a liability.

The audit's PoCs already show why Claim A is the stronger story: in every exploit, forged decisions included, the effect allowlist held.
